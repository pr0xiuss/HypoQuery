> **Note:** This document describes the architecture and implementation decisions for Phase 1 of HypoQuery. It focuses on the deterministic optimization engine and serves as a reference for future development phases.

# Phase 1 – Core Optimization Engine

## Objective

The objective of Phase 1 is to establish the deterministic foundation of HypoQuery before introducing distributed ingestion, retrieval-augmented generation (RAG), or large language models (LLMs).

Rather than relying immediately on AI-generated recommendations, the system is designed to first understand PostgreSQL execution plans, identify common performance bottlenecks using deterministic rules, and persist optimization data through a modular, extensible, and observable architecture.

This approach ensures that every optimization recommendation generated by future AI components is grounded in accurate execution plan analysis instead of relying solely on probabilistic reasoning.

---

## Goals

The primary goals of Phase 1 are:

- Build a reproducible PostgreSQL benchmarking environment.
- Execute categorized SQL workloads representing common performance scenarios.
- Collect execution plans using `EXPLAIN ANALYZE`.
- Parse PostgreSQL execution plans into recursive tree structures.
- Analyze execution plans using a modular rule engine.
- Generate structured optimization findings.
- Persist optimization runs, pipeline logs, and analysis results.
- Establish the foundation for observability across the optimization pipeline.

---

## Scope

At the completion of Phase 1, HypoQuery is capable of:

- Executing benchmark SQL workloads.
- Categorizing SQL queries by optimization scenario.
- Parsing query metadata from SQL benchmark files.
- Collecting PostgreSQL execution plans in JSON format.
- Constructing recursive execution plan trees.
- Traversing execution plans recursively.
- Detecting common optimization issues such as:
  - Sequential Scans
  - Nested Loop Joins
  - Hash Joins
  - Merge Joins
  - Sort Operations
  - Hash Aggregates
  - Bitmap Scans
  - Index Scans
  - Index Only Scans
  - High Shared Buffer Reads
  - Temporary Disk Writes
- Aggregating repeated optimization findings.
- Persisting optimization runs and findings into PostgreSQL.

---

## Architectural Principles

The implementation of Phase 1 follows several software engineering principles to ensure maintainability and extensibility.

### Modularity

Each responsibility is isolated into independent modules, allowing components such as collectors, parsers, analyzers, repositories, and services to evolve independently.

### Extensibility

The rule engine follows the Open/Closed Principle. New optimization rules can be introduced by implementing new rule classes without modifying the analyzer itself.

### Separation of Concerns

Responsibilities are clearly divided across the pipeline:

- Workload execution
- Execution plan collection
- Execution plan parsing
- Rule evaluation
- Optimization orchestration
- Persistence

Each component performs a single well-defined responsibility.

### Observability

Every optimization request is treated as an observable pipeline execution. Optimization runs, pipeline logs, execution plans, and optimization results are persisted to provide complete visibility into the optimization lifecycle.

---

## Deliverables

Phase 1 delivers the deterministic optimization engine that forms the foundation for every subsequent phase of HypoQuery.

Future phases—including live query ingestion, ELK integration, hybrid RAG orchestration, and HypoPG validation—will build upon this execution plan analysis engine rather than replacing it.

## Architectural Characteristics

The architecture intentionally separates data collection from analysis.

Rather than coupling SQL execution directly to optimization logic, execution plans are first transformed into a recursive domain model (`ExecutionPlan`). Every subsequent component operates on this model instead of raw PostgreSQL JSON.

This abstraction simplifies testing, enables recursive traversal of execution plans, and provides a stable interface for future components such as RAG retrieval, HypoPG validation, and AI-assisted optimization.

The architecture also follows a pipeline-based design where each stage produces a well-defined output that becomes the input for the next stage. This makes the optimization engine modular, extensible, and easier to maintain as new capabilities are introduced in future phases.

# 3. Execution Plan Processing

## Motivation

PostgreSQL returns execution plans as deeply nested JSON documents. Complex queries involving joins, subqueries, aggregations, and sorting often produce execution plans containing multiple levels of nested operations.

A simplified execution plan may look like:

```text
Hash Join
├── Seq Scan (orders)
└── Hash
    └── Seq Scan (customers)
```

Each node represents a different database operation and may itself contain child operations.

Analyzing only the root node would ignore the majority of the execution plan and lead to incomplete optimization recommendations.

For this reason, HypoQuery models execution plans as recursive tree structures rather than flat objects.

---

## Execution Plan Tree

The Explain Parser transforms PostgreSQL's JSON output into a recursive `ExecutionPlan` model.

```text
PostgreSQL EXPLAIN JSON
            │
            ▼
      ExplainParser
            │
            ▼
ExecutionPlan (Root Node)
            │
     ┌──────┴──────┐
     ▼             ▼
ExecutionPlan   ExecutionPlan
     │
     ▼
ExecutionPlan
```

Each node stores execution metadata together with references to its child nodes.

Examples of captured metadata include:

- Node Type
- Relation Name
- Schema
- Alias
- Join Type
- Parent Relationship
- Hash Condition
- Filter Condition
- Estimated Rows
- Actual Rows
- Startup Cost
- Total Cost
- Shared Buffer Statistics
- Temporary Disk Usage

This recursive representation mirrors PostgreSQL's internal execution plan structure while providing a clean object-oriented interface for analysis.

---

## Recursive Traversal

After parsing, the execution tree is traversed recursively by the `PlanAnalyzer`.

Rather than analyzing only the root operation, every node within the execution tree is visited exactly once.

```text
Hash Join
│
├── analyze(Hash Join)
│
├── Seq Scan
│      │
│      └── analyze(Seq Scan)
│
└── Hash
       │
       └── Seq Scan
              │
              └── analyze(Seq Scan)
```

Each node is evaluated independently against every optimization rule registered within the rule engine.

This traversal ensures that optimization opportunities embedded deep within execution plans are not ignored.

---

## Rule Evaluation

During traversal, each execution node is passed through a collection of modular optimization rules.

Examples include:

- Sequential Scan Rule
- Nested Loop Rule
- Hash Join Rule
- Merge Join Rule
- Sort Rule
- Hash Aggregate Rule
- Bitmap Scan Rule
- Index Scan Rule
- Index Only Scan Rule
- Shared Buffer Rule
- Temporary Write Rule

Each rule performs a deterministic evaluation based on the execution node and returns zero or more optimization findings.

Rules remain independent from one another, allowing new optimization strategies to be introduced without modifying existing logic.

---

## Finding Aggregation

Large execution plans frequently contain repeated operations.

For example:

```text
Hash Join
├── Seq Scan
└── Hash
     └── Seq Scan
```

Without aggregation, the analyzer would generate duplicate findings.

```text
Sequential Scan Detected
Sequential Scan Detected
```

Instead, HypoQuery aggregates repeated findings into a single structured recommendation.

Example:

```text
Sequential Scan Detected (2 occurrences)
```

This produces cleaner reports while preserving information about the frequency of each optimization opportunity.

---

## Benefits of the Recursive Design

Representing execution plans as recursive trees provides several advantages:

- Preserves PostgreSQL's native execution plan hierarchy.
- Enables analysis of every execution node rather than only the root operation.
- Simplifies implementation of recursive optimization algorithms.
- Supports future execution plan visualizations.
- Provides structured context for Retrieval-Augmented Generation (RAG).
- Enables richer optimization recommendations by exposing node-level metadata.
- Allows future extensions such as HypoPG validation without redesigning the parser.

The recursive execution plan model serves as the foundation for every optimization feature implemented in subsequent phases of HypoQuery.

# 5. Design Patterns

Phase 1 follows several object-oriented design patterns to improve modularity, extensibility, and maintainability. Rather than introducing patterns unnecessarily, each pattern was selected to solve a specific architectural problem.

---

## Repository Pattern

The Repository Pattern abstracts database operations behind dedicated repository classes.

Instead of embedding SQL queries directly inside business logic, repositories encapsulate all persistence-related operations.

Examples include:

- Product Repository
- Customer Repository
- Order Repository
- Inventory Repository
- Review Repository
- Product Event Repository
- Optimization Run Repository
- Optimization Result Repository
- Pipeline Log Repository

Benefits:

- Separates persistence from business logic.
- Simplifies unit testing.
- Allows storage implementations to evolve independently.
- Reduces SQL duplication.

---

## Strategy Pattern

The optimization rule engine is implemented using the Strategy Pattern.

Each optimization rule is represented as an independent class implementing a common interface.

Examples include:

- Sequential Scan Rule
- Nested Loop Rule
- Hash Join Rule
- Merge Join Rule
- Sort Rule
- Bitmap Scan Rule
- Index Scan Rule
- Shared Buffer Rule

The `PlanAnalyzer` simply executes every registered rule without knowing the implementation details of individual optimizations.

Benefits:

- New optimization rules can be added without modifying existing code.
- Rules remain completely independent.
- Encourages high cohesion and low coupling.

---

## Pipeline Pattern

The optimization workflow follows a pipeline architecture.

```
SQL Query
    │
    ▼
EXPLAIN Collector
    │
    ▼
Explain Parser
    │
    ▼
Execution Plan
    │
    ▼
Plan Analyzer
    │
    ▼
Optimization Findings
    │
    ▼
Persistence
```

Each stage performs one well-defined transformation before passing its output to the next stage.

Benefits:

- Clear execution flow.
- Easy debugging.
- Independent testing of pipeline stages.
- Simplified future extension.

---

## Composite Pattern

Execution plans are represented as recursive tree structures using the Composite Pattern.

Each `ExecutionPlan` object represents a single node while maintaining references to child execution plans.

```
Hash Join
├── Seq Scan
└── Hash
    └── Seq Scan
```

Both parent and child nodes are represented using the same class.

Benefits:

- Natural representation of PostgreSQL execution plans.
- Simplifies recursive traversal.
- Enables recursive optimization algorithms.

---

## Dependency Injection

Major components receive their dependencies through constructors rather than creating them internally.

Examples include:

- Collectors receiving database connections.
- Services receiving repositories.
- Workload receiving runners.
- Seeders receiving repositories.

Benefits:

- Reduces coupling.
- Simplifies testing.
- Makes components reusable.
- Improves maintainability.

---

## Layered Architecture

The overall system follows a layered architecture.

```
Presentation (Future API)
          │
          ▼
Service Layer
          │
          ▼
Analysis Layer
          │
          ▼
Repository Layer
          │
          ▼
Database
```

Each layer communicates only with the layer directly beneath it.

Benefits:

- Separation of concerns.
- Easier maintenance.
- Better scalability.
- Clear architectural boundaries.

---

## Why These Patterns?

The selected design patterns prioritize maintainability and extensibility over premature optimization.

As future phases introduce live query ingestion, Redis queues, ELK integration, Retrieval-Augmented Generation (RAG), and HypoPG validation, the existing architecture can be extended by introducing new components rather than modifying existing ones.

This minimizes architectural changes across future development phases while keeping each module focused on a single responsibility.


| Design Pattern | Implementation | Purpose |
|----------------|----------------|---------|
| Repository Pattern | `repositories/`, `observability/repositories/` | Encapsulates all database operations and separates persistence from business logic. |
| Strategy Pattern | `observability/analyzers/rules/` | Implements each optimization rule as an independent strategy, allowing new rules to be added without modifying the analyzer. |
| Pipeline Pattern | `optimization_pipeline_service.py` | Organizes the optimization workflow into sequential processing stages where each component performs a single responsibility. |
| Composite Pattern | `ExecutionPlan` | Represents PostgreSQL execution plans as recursive tree structures, enabling uniform traversal of parent and child nodes. |
| Dependency Injection | Services, Collectors, Seeders, Repositories | Supplies dependencies through constructors, reducing coupling and improving testability. |
| Layered Architecture | Entire project structure | Separates infrastructure, workload execution, analysis, and persistence into independent architectural layers. |

Overall, these design patterns enable HypoQuery to remain modular, extensible, and maintainable while providing a solid architectural foundation for future phases, including production query ingestion, ELK-based observability, Retrieval-Augmented Generation (RAG), and HypoPG-driven validation.

Rather than allowing every component to communicate directly with one another, HypoQuery follows a unidirectional dependency flow.

Each layer depends only on the layer immediately below it, preventing circular dependencies and reducing coupling between modules.

## Dependency Direction

The dependency graph follows a top-down architecture.

```text

            │
            ▼

            │
            ▼
Collector → Parser → Analyzer
            │
            ▼

            │
            ▼
```

Lower layers never depend on higher layers.

For example:

- The parser does not know about repositories.
- Rules do not know about PostgreSQL.
- Collectors do not know about optimization findings.
- Repositories do not know how execution plans are analyzed.

This separation minimizes coupling and makes each component independently testable.

# 8. SOLID Principles

Phase 1 was designed with the SOLID principles in mind to ensure the optimization engine remains modular, extensible, and maintainable as additional capabilities are introduced in future phases.

Rather than applying SOLID as a theoretical exercise, each principle is reflected through concrete architectural decisions within the codebase.

---

## Single Responsibility Principle (SRP)

Every class within the optimization pipeline is responsible for one well-defined task.

Examples include:

| Component | Responsibility |
|-----------|----------------|
| ExplainCollector | Collect execution plans from PostgreSQL. |
| ExplainParser | Parse PostgreSQL JSON into recursive execution plans. |
| PlanAnalyzer | Traverse execution plans and execute optimization rules. |
| OptimizationPipelineService | Coordinate the complete optimization workflow. |
| QueryCatalog | Load benchmark SQL queries. |
| MetadataParser | Parse metadata from SQL benchmark files. |
| ProductSeeder | Generate and persist benchmark products. |
| ProductRepository | Persist product data. |

By isolating responsibilities, individual components can evolve independently without affecting unrelated parts of the system.

---

## Open/Closed Principle (OCP)

The optimization engine is designed to be extended without modifying existing components.

The clearest example is the rule engine.

New optimization rules can be introduced simply by implementing a new rule class and registering it within the analyzer.

Existing rules remain unchanged.

Examples include:

- Sequential Scan Rule
- Nested Loop Rule
- Hash Join Rule
- Merge Join Rule
- Sort Rule
- Bitmap Scan Rule
- Index Scan Rule

This allows the optimization engine to grow without introducing regression risks into existing logic.

---

## Liskov Substitution Principle (LSP)

Optimization rules inherit from a common base rule interface.

Each rule can replace another without changing the behavior of the analyzer.

The `PlanAnalyzer` treats every optimization rule identically and depends only on the shared contract rather than specific implementations.

This enables new rules to integrate seamlessly into the analysis pipeline.

---

## Interface Segregation Principle (ISP)

Interfaces remain focused and lightweight.

For example:

- Seeder interface defines only seeding responsibilities.
- Rule interface defines only optimization rule behavior.

Components are not forced to implement methods they do not require.

This keeps abstractions small and prevents unnecessary coupling.

---

## Dependency Inversion Principle (DIP)

High-level services depend on abstractions rather than implementation details.

Examples include:

- Pipeline services depend on repositories.
- Collectors receive database connections through dependency injection.
- Seeders receive repositories instead of creating them internally.

Dependencies are supplied externally through constructors rather than instantiated directly.

This makes the system easier to test, maintain, and extend.

---

## Summary

Applying the SOLID principles throughout Phase 1 resulted in a modular architecture where each component performs a single responsibility while remaining loosely coupled to the rest of the system.

As future phases introduce distributed ingestion, Redis queues, ELK integration, Retrieval-Augmented Generation (RAG), and HypoPG validation, the existing architecture can be extended by introducing new components instead of rewriting existing ones.

This significantly reduces maintenance effort while improving long-term scalability.

# 9. Current Limitations

Although Phase 1 establishes a strong deterministic optimization engine, the project intentionally limits its scope to execution plan analysis and benchmark workloads.

Several capabilities have been deferred to later phases to avoid unnecessary architectural complexity during the foundation stage.

---

## Static Benchmark Workloads

Phase 1 executes predefined SQL benchmark queries stored within the workload catalog.

Current implementation:

- Categorized benchmark queries
- Metadata-driven execution
- Reproducible workload generation

Limitation:

The system does not yet analyze live production workloads.

Planned Solution:

Integrate `pg_stat_statements` to continuously collect frequently executed and slow SQL queries from PostgreSQL.

---

## No Live Query Ingestion

Execution plans are currently collected only for manually executed benchmark queries.

Limitation:

The optimization pipeline is not yet connected to a continuous ingestion system.

Planned Solution:

Introduce an ingestion pipeline using:

- pg_stat_statements
- auto_explain
- Redis
- Background workers

This will allow HypoQuery to analyze production workloads automatically.

---

## Deterministic Rule-Based Optimization

Current optimization recommendations are generated using deterministic rules.

Examples include:

- Sequential Scan detection
- Join analysis
- Buffer analysis
- Temporary write detection

Limitation:

Recommendations remain rule-based and do not yet leverage semantic reasoning.

Planned Solution:

Introduce a Retrieval-Augmented Generation (RAG) pipeline that combines deterministic findings with contextual knowledge retrieved from documentation, historical optimizations, and schema metadata.

---

## No Hypothetical Index Validation

Current recommendations are not validated against PostgreSQL.

Limitation:

The system cannot determine whether a suggested index would actually improve execution cost.

Planned Solution:

Integrate the HypoPG PostgreSQL extension to create hypothetical indexes, re-execute execution plans, and compare optimization costs before presenting recommendations.

---

## Local Observability Storage

Optimization runs, pipeline logs, and optimization results are currently stored within PostgreSQL.

Limitation:

Observability data cannot yet be explored through centralized dashboards.

Planned Solution:

Integrate the ELK stack:

- Elasticsearch
- Logstash
- Kibana

This will provide searchable execution history, dashboards, and historical performance analysis.

---

## No Distributed Processing

Phase 1 executes the optimization pipeline synchronously.

Limitation:

The system is not yet capable of handling large-scale concurrent optimization requests.

Planned Solution:

Introduce:

- Redis queues
- Load-shedding distributor
- Background workers
- Asynchronous processing

to support scalable execution.

---

## Summary

The limitations of Phase 1 are intentional architectural decisions rather than missing functionality.

The primary objective of this phase was to establish a reliable, deterministic optimization engine capable of understanding PostgreSQL execution plans through recursive analysis and structured rule evaluation.

Subsequent phases will extend this foundation with production query ingestion, distributed processing, centralized observability, Retrieval-Augmented Generation (RAG), and hypothetical optimization validation while preserving the architecture established in Phase 1.
